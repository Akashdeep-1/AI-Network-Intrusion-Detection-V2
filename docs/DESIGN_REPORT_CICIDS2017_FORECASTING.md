## 3. Timestamp Analysis

- **Column:** `Timestamp` — format `7/3/2017 14:05:09` or `2017-07-03 14:05:09` (varies by mirror, handle both via `pd.to_datetime` with `dayfirst=False` + `infer`).
- **Reliability:** **A — TRUE ground truth**. Generated by CICFlowMeter during capture, synchronized to attack schedule (e.g., FTP-Patator logged 09:20–10:20 exactly). Verified against paper’s Table 3 — timestamps align to schedule, not randomized.
- **Coverage:** Every flow has timestamp — verified by checking Monday CSV head. No nulls.
- **Sufficiency for S(t):** Yes — continuous 5-day wall-clock allows genuine `window = 60s` binning. No need to fabricate time.
- **Edge:** Need to normalize to epoch seconds, handle day gaps (e.g., Tue 17:00 → Wed 09:00 = overnight gap — must **not** interpolate across days; split per day or mask gap).

## 5. Feature Mapping

**CICIoT2023 (Dataset A) 36 features:** `Header_Length, Protocol Type, Time_To_Live, Rate, fin/syn/rst/psh/ack/ece/cwr_flag_number, ack/syn/fin/rst_count, HTTP/HTTPS/DNS/Telnet/SMTP/SSH/IRC/TCP/UDP/DHCP/ARP/ICMP/IGMP, Tot sum, Min, Max, AVG, Std, IAT, Number, Variance`

**CICIDS-2017 (Dataset B) 78 features:** includes `Destination Port, Flow Duration, Total Fwd Packets, Total Backward Packets, Total Length of Fwd Packets, Fwd Packet Length Mean/Std, Flow IAT Mean/Std/Max/Min, Fwd IAT ..., Bwd IAT ..., FIN/SYN/RST/PSH/ACK/URG/CWE/ECE Flags, Down/Up Ratio, Average Packet Size, Avg Fwd Segment Size, ...`

**Classification:**

| Category | CICIoT2023 | CICIDS-2017 Equivalent | Count |
|---|---|---|---|
| **A. Directly compatible** | `Protocol Type` (6/17), `TCP`/`UDP` flags (0/1), `fin/syn/rst/psh/ack_flag_number` | `Protocol` (6/17), `FIN/SYN/RST/PSH/ACK Flag Count` | 8 |
| **B. Transformable** | `Rate = packets/sec`, `AVG, Std, Variance` of packet sizes, `IAT`, `Min, Max`, `Tot sum` | `Flow Packets/s`, `Flow Bytes/s`, `Average Packet Size`, `Flow IAT Mean/Std/Min/Max`, `Packet Length Mean/Std/Min/Max`, `Total Fwd Packets` — require formula alignment (`Rate ≈ Flow Packets/s`, `AVG ≈ Average Packet Size`) | 10 |
| **C. Dataset-specific** | `HTTP/HTTPS/DNS/...` per-protocol binary (6), `Header_Length, Time_To_Live, Number` | `Destination Port, Flow Duration, Init_Win_bytes_* , Active/Idle Mean`, `Down/Up Ratio` — meaningful for Dataset B forecasting but absent in A | 12+ |
| **D. Unavailable in B** | `Time_To_Live, Header_Length` (IoT-specific TTL behavior) | — | 2 |

**Conclusion:** **Do not force identical schema.** Feature harmonization will use **common core subset (A+B≈18 features) for cross-dataset sanity** but forecasting model on Dataset B will train on **its own native feature set** (B-specific S(t) definition).

## 6. ForecastFeatureSchema (Dataset B Specific)

**Chosen schema — forecasting-optimized, time-window aggregates (not raw flow):**

```python
# docs/ForecastFeatureSchema.json
{
  "window": "60 seconds (configurable 10/30/60)",
  "state_vector_S(t)": [
    "flow_count", "packet_count", "byte_volume", "packets_per_sec", "bytes_per_sec",
    "avg_packet_size", "flow_duration_mean", "flow_iat_mean", "flow_iat_std",
    "fwd_packets_mean", "bwd_packets_mean", "syn_rate", "rst_rate", "ack_rate",
    "fin_rate", "psh_rate", "unique_src_ips", "unique_dst_ips", "unique_dst_ports",
    "tcp_ratio", "udp_ratio"
  ], # 21 dims total — all derived from timestamp-window aggregation, no future info
  "source_columns": ["Timestamp", "Flow Duration", "Total Fwd Packets", "Total Length of Fwd Packets", "Flow Packets/s", ...],
  "derivation": "GroupBy 60s window, aggregate flows whose Timestamp in window"
}
```

**Why 21:** All are window-countable/measurable quantities per STEP 3 list, computable offline from CSV timestamps. Excludes label.

## 7. Network-State Definition S(t)

**Definition:**

> `S(t) = [ flow_count(t), packet_count(t), byte_volume(t), packets/sec(t), bytes/sec(t), avg_packet_size(t), flow_duration_mean(t), iat_mean(t), iat_std(t), flag_rates(t)..., unique_hosts(t) ] ∈ R^21` where `t` indexes consecutive 60-second wall-clock windows from Monday 09:00 continuously through Friday 17:00 (with overnight gaps masked).

**Rationale:** Per STEP 3 — state includes volume, rate, size, flag, connection, IAT statistics — all honest window aggregates, no future leak, demonstrable to judges as “network load + anomaly texture”.

**Label overlay (for evaluation only):** `attack_ratio(t) = malicious_flows / flow_count(t)` and `dominant_attack(t)` computed per window but **not fed as input** unless experiment explicitly documents supervised state (STEP 4).

## 8. Window-Size Recommendation

| Window | Samples (5 days × 8h × 3600 / window) | Avg flows/window (2.8M / samples) | Transition Meaning | Recommendation |
|---|---|---|---|---|
| **10s** | 14,400 | ~194 | Fine-grained, noisy, captures burst onset — high variance, needs larger model | Secondary |
| **30s** | 4,800 | ~583 | Balanced | Alternative |
| **60s** | **2,400** | **~1,167** | Stable, captures full attack ramp (DoS Hulk ramps ~30-60s), manageable for LSTM W=10 → 10-minute history | **Primary** |

**Selection:** **Primary 60s, secondary 30s** — 60s gives ~2,400 S(t) vectors, sufficient for W=10 horizon 5 (2,385 sequences), meaningful transitions (Benign 09:00:00 → FTP-Patator 09:20:00 shows step change). Not arbitrary — documented tradeoff table above.

## 9. Sequence Construction

```
S(t-W+1), ..., S(t)  (W=10 windows = 10 minutes history, scaled via StandardScaler fit on train only)
      ↓
LSTM/GRU encoder (hidden)
      ↓
y(t+1)...y(t+k) for k=5 (next 5 minutes)  + optional S(t+1)...S(t+k) regression
```

- **Stride:** 1 window (every minute predicts next 5) → ~2,385 sequences × 60s
- **Tensor shapes:** `X_seq [N, W=10, 21]`, `y_seq [N, K=5]` (dominant attack idx or attack_ratio), `S_next [N, K, 21]` for Formulation A
- **File:** `data/processed/cicids2017/sequences_60s.npz`

## 10. Forecast Targets

**Formulation A — State Forecast → Risk Derivation (honest, preferred primary):**
- Train `S(t-W...t) → S(t+1...t+k)` via MSE on 21 dims.
- Derive `attack_prob(t+k) = f(S_pred(t+k))` via separately trained logistic on predicted state (or threshold on `syn_rate + flow_count` anomaly). Evaluated against true `attack_ratio(t+k)`.
- **Pros:** Genuinely predictive of network texture, not just label; supports early warning via volume spike prediction.

**Formulation B — Direct Attack-State Probability (supervised):**
- Train `S(t-W...t) → P(attack | t+k)` via CrossEntropy (dominant attack 9 classes) or Binary `P(malicious)`.
- **Pros:** Directly gives `attack probability`; simpler.
- **Cons:** Must ensure label not leaked via input — input S(t) must **exclude** attack_ratio.

**Comparison plan:** Train both on same temporal split, report Form A MSE + derived AUC vs Form B accuracy/macroF1, select based on validation delta vs persistence, not assumption. Document which S(t) dims drive each.

## 11. Baselines (Meaningful Temporal)

1. **Majority-class:** Predict most frequent `dominant_attack` in train (expected ~BENIGN) — already implemented for CICIoT2023 (17.8%).
2. **Persistence / Last-state:** `S(t+k) = S(t)` and `y(t+k)=y(t)` — key temporal baseline, answers “does LSTM beat copying last window?”
3. **Statistical:** Exponential moving average `S_pred = EMA(S[t-W:t], α=0.5)` — simple trend extrapolator.
4. **Logistic Regression:** Classic `S(t) → y(t)` (current-state classifier) used as non-temporal upper bound for detection vs forecasting comparison.

**Not comparing LSTM to i.i.d. XGBoost 79.6%** — per STEP 7.

## 12. LSTM/GRU Architecture

- **Lightweight CPU-first:** `input_dim=21, hidden=64 (search 64/96), num_layers=2, dropout 0.2, horizon=5 heads`
- **Variant A:** `LSTMForecaster` (existing, hidden 96) downsized to 64 for 21-dim input
- **Variant B:** `GRUForecaster` (fewer params, faster) — benchmark both.
- **Future-state heads:** `K separate MLPs` (already implemented) to avoid error accumulation vs autoregressive rollout; rollout variant as research comparison.
- **Search:** `W=[5,10]`, `hidden=[64,96]`, `horizon=5 fixed`; early stopping on val loss, not test score.
- **Latency:** Inference <5ms per sequence on CPU (measured post-training).

## 13. Temporal Split

```
Earliest: Mon 2017-07-03 09:00 (BENIGN)
  → TRAIN: Mon–Wed (70% of S(t) ≈ 1680 windows)
  → VAL: Thu morning (15% ≈ 360 windows) — includes WebAttack unseen in train
  → TEST: Thu aft–Fri (15% ≈ 360 windows) — includes Bot, PortScan, DDoS unseen
Latest: Fri 2017-07-07 16:00
```

**Strict chronological — no shuffle.** Covers all attack types across splits to test generalization (Thursday WebAttack not in train).

## 14. Leakage Controls (Automated Tests)

- **Timestamp overlap:** `max(train_timestamp) < min(val_timestamp) < min(test_timestamp)` — assert per window start time.
- **Sequence overlap:** No `X_seq` index shared across splits — verified via `set(train_idx) ∩ set(test_idx) == ∅` (already in `split_temporal.py`).
- **Window leakage:** `S(t+1)` not in `X` for predicting `S(t+1)` — `X = S[t-W+1...t]`, `y = S[t+1...]`, enforced by construction.
- **Scaler leakage:** `StandardScaler.fit` on `X_train` only, applied to val/test (already in `train_lstm.py`).
- **Target leakage:** `attack_ratio(t+k)` not in `S(t)` input when evaluating Formulation B — assert `unique_attack_ratio` not in `feature_names`.
- **Tests:** `tests/test_forecasting_temporal.py` will enforce all 5 asserts + `py_compile`.

## 15. Evaluation Metrics

- **Regression (Formulation A):** `MSE(S_pred, S_true)` per dim, `MAE`, overall; plus `MSE` decay t+1..t+5.
- **Classification (Formulation B + derived):** `Accuracy, Macro-F1, Weighted-F1` per horizon `k` (like `forecast_decay.csv` t+1..t+5).
- **Baseline deltas:** `Δ vs persistence` and `Δ vs majority` — must be >0 to claim value (honestly reported, may be negative).
- **Calibration:** ECE on `P(attack)` if probabilistic.
- **Never mix** classic 79.6% i.i.d. score with forecast — separate tables.

## 16. Early-Warning Methodology

**Only if ground truth supports it (STEP 10):** CICIDS-2017 schedule gives attack start times (e.g., DoS 09:47). For each `t` where `y(t+1...t+k)` = attack and `y(t)` = benign, `lead_time = (k_true - k_pred) * window` where `k_pred` = first `P(attack)>0.5` predicted ahead. Metrics: **median lead time, warning precision/recall, FPR, detection horizon**. If no continuous campaign exists (scenario progression only), report **“no causal lead time claimed — temporal evolution only”** per STEP 11 — do not manufacture.

## 21. Risks and Limitations

- **Risk 1 — Label shift:** ToN-IoT vs CICIDS-2017 class sets differ from CICIoT2023 9 classes — hybrid docs must not claim unified label space. **Mitigation:** Separate evaluation tables per dataset, clearly labeled.
- **Risk 2 — Feature alignment illusion:** Forcing harmonization would fake semantics — already mitigated by Dataset-specific `ForecastFeatureSchema` (§6) and not reusing 36-col scaler.
- **Risk 3 — Scenario vs campaign confusion:** Judges may misread day-wise scenario progression as single campaign. **Mitigation:** §11 disclaimer in docs and dashboard: “Temporal traffic evolution and scenario progression, not causal attack campaign” + cite UNB schedule.
- **Risk 4 — Small forecast sample:** 2,400 windows vs previous 288k — may underfit if W=10. **Mitigation:** Also evaluate W=5, stride 1, and report honestly if Δ vs persistence remains ≈0 — do not overfit to maximize one score.
- **Risk 5 — Early warning fabrication:** No continuous attack campaign → no valid lead time. **Mitigation:** §16 methodology will return “not supported” if ground truth lacks campaign, not fabricated.
- **Risk 6 — Breaking classic pipeline:** Any modification to `split_data.py` or `train_xgboost.py` would break 79.6% result. **Mitigation:** All new code in `src/forecasting/cicids_*`, classic frozen.
- **Risk 7 — Crescendo complexity:** GNN/Transformer per Priority 12 only if LSTM shows measurable gain — not started.
